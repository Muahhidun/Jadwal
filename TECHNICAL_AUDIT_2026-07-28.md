# Dauam — технический аудит и план стабилизации

**Дата фиксации:** 28.07.2026
**Статус:** рабочий источник правды для следующих итераций
**Область проверки:** Flutter, iOS, Android, WidgetKit, Apple Watch, AlarmKit, Siri/App Intents, Live Activity, уведомления, контент, тесты и состояние Git.

## 1. Итог

Antigravity и Codex сделали большой объём реальной работы: основной iPhone-интерфейс, виджеты, StandBy и Apple Watch уже находятся на уровне функционального расширенного MVP. Однако проект пока нельзя считать готовым к закрытой бете.

Главная задача следующего цикла — не добавлять новые функции, а сделать текущую версию:

1. сохранённой и полностью восстанавливаемой через Git;
2. воспроизводимо собираемой с чистого состояния;
3. надёжной по уведомлениям и нативным функциям;
4. безопасной по религиозному контенту и продуктовым ограничениям.

## 4. Критические расхождения и риски

### 4.1 Git и воспроизводимость — P0

Продвинутая текущая версия приложения не сохранена как целостный коммит. Нельзя начинать рискованные исправления, пока не создана безопасная контрольная точка.

### 4.2 Release-сборки — P0

Закрыто 28.07.2026: обе платформы собираются с чистого состояния. Для публикации Android остаётся операционная задача — создать отдельный upload keystore; его отсутствие больше не подменяется debug-подписью.

### 4.3 Надёжность уведомлений — P0

Текущая очередь ограничена 58 уведомлениями и при включённых сценариях покрывает ориентировочно 5–6 дней, а не обещанные планом 10–14.

Также отсутствуют:

- `BGAppRefreshTask` для iOS;
- фоновое продление очереди на Android;
- последнее мягкое уведомление с просьбой открыть приложение перед исчерпанием очереди;
- длительный реальный тест доставки.

### 4.4 Контент — P0 перед публичной бетой

В `adhkar.json` 39 записей, но все имеют статус черновика. До внешнего релиза владелец/специалист должен подтвердить арабский текст, транслитерацию, перевод и источник каждой записи.

### 4.5 Продуктовые ограничения

Перед релизом необходимо удалить или переименовать остатки терминологии повторных нажатий:

- `ZikrTickIntent`;
- «Отметить повторение».

Никаких цифровых счётчиков зикра или действий, имитирующих тасбих, быть не должно.

### 4.6 Дополнительные технические риски

- текущий build ID принудительно сбрасывает онбординг — это допустимо для внутренней разработки, но не для обновлений пользователей;
- завершение TTS сейчас может автоматически отметить весь сборник выполненным;
- нативные функции почти не покрыты тестами;
- `PLAN.md` и `AGENTS.md` частично противоречат фактическому состоянию и используют старое название Jadwal.

## 5. Порядок работ

### Шаг 1. Безопасная контрольная точка Git

Цель: сохранить текущую рабочую версию без изменения поведения приложения.

Работы:

1. создать отдельную ветку стабилизации;
2. отделить исходники от производных файлов;
3. добавить корректные правила `.gitignore`;
4. не удалять пользовательские материалы и rollback-копии;
5. зафиксировать исходники Flutter, iOS, Watch, WidgetKit и документацию;
6. проверить, что после коммита рабочее дерево понятно и откат возможен.

Критерий готовности:

- текущая версия восстановима из Git;
- `build`, временные логи и тяжёлые QA-артефакты не попали в коммит;
- состав сохранённых файлов показан владельцу;
- никакой функционал и визуал не изменились.

### Шаг 2. Воспроизводимые iOS и Android release-сборки

Цель: получить честную базовую сборку обеих платформ до следующих изменений.

Работы:

1. исправить Android core library desugaring;
2. подготовить корректную release-подпись без debug key;
3. устранить iOS/Watch asset build failure;
4. собрать все iOS target-ы с чистого состояния;
5. выполнить `flutter analyze`, `flutter test`, Android release и iOS release;
6. установить чистую iOS-сборку на iPhone и Apple Watch и провести короткий smoke-test запуска.

Критерий готовности:

- обе release-сборки завершаются успешно;
- iPhone, Watch, WidgetKit и основное приложение запускаются из этой сборки;
- ошибки и точные команды проверки записаны в этот аудит.

### Шаг 3. Надёжность уведомлений

- пересчитать реальную ёмкость очереди;
- обеспечить заявленные 10–14 дней или честно изменить архитектурное обещание;
- добавить фоновое продление и последнее резервное уведомление;
- провести многодневный тест iPhone и Android.

### Шаг 4. Нативные функции

- финальный AlarmKit-тест;
- Siri/App Intents RU/KZ;
- Live Activity/Dynamic Island lifecycle;
- единая семантическая хаптика;
- нативные smoke/integration tests.

### Шаг 5. Закрытие функциональных пробелов MVP

- фиксированное время пользовательского напоминания;
- месячный экран времён;
- месячная сводка постоянства;
- размер арабского шрифта;
- корректное ручное завершение после TTS.

### Шаг 6. Контент и закрытая бета

- утверждение 39 зикров;
- финальный RU/KZ-проход;
- TestFlight;
- Google Play Internal Testing;
- проверка уведомлений на реальных устройствах.

## 6. Правило обновления аудита

После каждого завершённого шага:

1. отметить результат и дату;
2. приложить команды/тесты, которыми результат подтверждён;
3. записать оставшиеся риски;
4. только после этого переводить следующий шаг в работу.

Этот файл остаётся рабочим источником правды до синхронизации и обновления `PLAN.md`.
